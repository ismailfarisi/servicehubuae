As of 2026-05-29, **production** still runs on **AWS**, not Netcup (the Netcup migration in [[project_infra_migration_target]] / [[project_netcup_staging_live]] is staging/target only). Prod = one EC2 box `i-0f982d225cd7f140a` (`mypickuae-production`, t3a.large, ap-south-1, ~8GB, no swap) running docker-compose for 9 services + Typesense + Caddy; Postgres is RDS (`mypickuae_production` DB), Redis is ElastiCache. The on-box compose `/opt/mypickuae/docker-compose.yml` is generated by `terraform/production/user-data.sh` (only on instance launch) — a normal deploy just `docker-compose pull && up --force-recreate`, it does NOT rewrite the compose. So a config change to user-data.sh must ALSO be patched onto the live box to take effect before the next instance replacement.

**Operate prod with no SSH** via `aws ssm send-command` (AWS user = `terraform`, account 100137600454). jq isn't installed locally — pass `--parameters file://<json>`.

**Storefront product listing is 100% Typesense-backed** (`/products` → `total = result.found`, no DB fallback). So if products are missing on the storefront, it's almost always a **stale/incomplete Typesense index**, not a DB problem. Only `status='published'` products are indexed; catalog-import creates products as `draft` by default. Fix = full reindex: enqueue the BullMQ `search-reindex` queue (job name `reindex`) — the worker lives in product-service. Inside the container: `docker exec -w /app/apps/product-service mypickuae-product-service-1 bun -e '...Queue("search-reindex").add("reindex",{...})'`.

**Why this bit us:** product-service `mem_limit` was 384m and the reindex (batches of 100 products × all relations) OOM-killed bun after batch 1, leaving the index permanently stale (only oldest ~100 products / 1 vendor visible). Fixed by bumping to 1g (PR #207). If a service silently misbehaves in prod, check `dmesg | grep -i 'out of memory'` and `docker inspect ... RestartCount` — services are capped at 384m with no swap.
